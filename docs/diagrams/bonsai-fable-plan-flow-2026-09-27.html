The two speed-ups, plainly

The optimize round measured a failed chart-bug run and found 81% of the time was the model re-reading its own memory. These are the picks that went into tonight’s runs (their numbers are the option numbers from the round — option 2 was left as the fallback).

pick 1Memory kept across trims

Before: when the conversation’s memory filled and old output was trimmed, the engine forgot everything it had read and re-read its whole remaining memory — 4 min 14 s in the measured run.

Now: one engine switch (--cache-reuse 256) lets it keep what it already read. An old test explicitly forbade this switch with no reason recorded anywhere; it was flipped, with the 4:14 measurement written into the test as the reason. Because it was never tried here, tonight’s live check measures it directly and prints WORKS or did NOT help.

pick 3High instructions read ahead

Before: the first rescue of a session paid ~25–30 s reading the High-effort instructions before it could start.

Now: about 2.5 s after Bonsai starts, it quietly reads those instructions into the spare slot and saves that reading (skipped if the slot is busy). The first rescue restores the saved reading and starts right away.

pick 2 · not builtSummarize instead of the big trim

The fallback: instead of trimming old output and letting the model re-read, write a short summary of the old steps.

Only gets built if pick 1’s switch misbehaves in tonight’s checks — then it becomes tomorrow’s plan.
