Bonsai vs the chart bug

25 September 2026 · Can Bonsai 2 27B fix a real bug in MAIN2026? The symbol search list on the price chart hides behind the EMA legend. Two tries in throwaway copies, Effort Off, 32k memory, everything approved automatically inside the safety fence.

0 / 2tries fixed it

Not fixed in either try, and nothing was changed. Bonsai never opened the chart code. It spent its tries on two unrelated checks that only looked broken.

What stopped it: in bug-fix mode Bonsai scores every attempt with the project's own test command. In MAIN2026 that's about 9,500 tests, taking 3 min 17 s. Bonsai cuts a test run off at 2 minutes, and the cut-off run left two documentation checks marked "failed", so it chased those. The model itself never got a real look at the bug.

The bug

Type in the symbol box on the price chart and a list of matches opens under it. The legend rows "EMA 13 · 21" and "Vol" draw on top of that list. The pictures are from the offline chart after typing "GC". It has no gold data, so the list says "nothing matched", but the layering is the same as on the live site.

  1. The list lives inside the chart's header strip. The strip and the legend are both on layer 4.
  2. When two things share a layer, whichever the page adds later is drawn on top. The legend is added later, so it covers the list.
  3. The list is set to layer 80, but nothing inside the strip can rise above the strip's own layer.

The fix: move the strip up one layer, at desks/chart/index.html:629. The toolbar buttons on the right are on layer 6, so they still sit above the strip.

.hud{position:absolute;left:0;right:0;top:0;z-index:4;…}   →   .hud{…;z-index:5;…}

Where the time went

Both tries spent their first 2 minutes on the project's full test suite, which never finished, then all the rest on fix attempts aimed at the wrong thing.

Why it failed

  1. It read the request as a bug fix. That mode starts by running the project's tests to find what's failing.
  2. The project's tests are too big for it. npm test in MAIN2026 runs about 9,500 tests and takes 3 min 17 s even with nothing else running. Bonsai stops any test run at 2 minutes.
  3. The cut-off run looked like a failure. Two slow documentation checks were caught mid-run and marked failed. Run on their own, all 61 of those checks pass.
  4. It chased the wrong failure. The bug has no test, so Bonsai took those two checks as "the bug". In try A it picked an unrelated old file to change. In try B it picked the check file the request named, and tried to "fix" the check itself.
  5. It could never succeed. Every attempt was scored by the same 9,500 tests, which were cut off at 2 minutes every time. In try B, the check named in the request was never used for scoring.

What would let Bonsai fix bugs like this

Not built; the next steps if you want them. These are changes to Bonsai's fix mode, not the model.

  1. Use the check the request names. If the request gives a command that fails, score attempts with that command, not npm test.
  2. Don't treat a cut-off test run as a failure. When the project's tests hit the time limit, say so and skip ahead, instead of reading the half-finished run as a list of failures.
  3. Ignore failures that don't match the request. Nothing in "the symbol search dropdown is hidden behind the EMA legend" relates to documentation checks.
  4. Search the code for the request's words first. "symbol", "legend" and "EMA" lead straight to desks/chart. A visual bug like this one has no test, so Bonsai should make its own check (like the judge) before editing.
