Editing Bonsai's weights

What it would take to change the 27B model's weights from the Weights tab and run Bonsai on the result: how it works today, what an edit can be, two ways to do it with their pros and cons, and the order to build it in.

The answer

Yes, it can be done, but not by rebuilding. The model is a data file, and the running model only reads it once.

1
The build never touches the model

Typing bonsai rebuilds Bonsai's own code when it changed. The 7.2 GB model is a separate file that Prism ML trained. Nothing in the repo builds it.

2
A running model can't see changes

The model server loads the file when it starts and keeps it for the whole run. A change needs either a restart or a side file the server was told about at start.

3
Two routes work

Save and restart: write the change into a copy, restart on it. Proven today. Live side file: a small file of changes whose strength moves while Bonsai runs. Needs one test first.

How it works today

Four parts, and only one of them is ever rebuilt.

1 · the model file
7.2 GB of weights

In ~/.bonsai-code/models. Trained by Prism ML. Fingerprinted by bonsai setup.

2 · the model server
Loads the file once

Started by Bonsai, kept loaded 30 minutes after you quit. Never re-reads the file while running.

3 · Bonsai
Talks to the server

Its warm-up (the instructions already read) is saved and reused on the next start.

4 · the Weights tab
Reads the file

Opened with /weights. Reads only the bytes it shows. Never writes.

The “build” step is the bonsai command checking Bonsai's code and recompiling the app, in about 0.2 seconds. It looks at the repo only, never at the model file.

What an edit can be

The file does not hold weights as plain numbers, and that decides which edits are clean.

How one row is stored

weight = digit × scale

Every digit is −1, 0 or +1, and one scale is shared by each run of 128 digits:

−10+1+10−1+10−1−10+10+1−10

…128 digits, then one scale such as 0.0176, repeated along the row.

Before storing, each row was also mixed: a fixed recipe, a Hadamard mix with sign flips, spreads every weight across 1,024 stored digits. That helps two bits lose less. It is also why the stored digits look like static.

One real weight lives in 1,024 digits

Each bar is a stored digit that carries part of the one weight you picked.

So you can't set a single weight to a chosen number. Saving it would mean re-rounding 1,024 digits to −1, 0 or +1, and that rounding adds error about as big as a typical weight, to all 1,024 of them.

What is clean: multiplying a whole row. A row's scales carry the row's size, so changing them scales every weight in that row exactly, and nothing else.

Two ways to do it

Both start the same way: an Edit panel in the Weights tab where you pick a row or channel, set how much to turn it up or down, and see a list of your changes with undo. They differ in how the model gets the change.

A · Save and restart proven format

  1. Save writes your list into an edited copy of the model. The copy is a disk clone, so it is instant and takes no space until blocks change.
  2. Bonsai gets a second model choice, “27B · edited”, in /model.
  3. Picking it restarts the model on the copy. It reads Bonsai's instructions again with the new weights.
  4. Run a question or the practice tasks to see what changed.

Pros

  • Uses the file format the Weights tab already decodes byte for byte.
  • No change to the engine. Same speed as the original, apart from the helper.
  • The edit is saved for good and survives restarts.
  • Almost no disk: 26 GB is free, and the clone uses none of it.
  • Undo is picking the original model again.

Cons

  • Not real time: every change waits about 40 seconds for the restart and re-read.
  • Only whole-row edits are exact. Input channels are not.
  • Needs the warm-up fix first, or old saved warm-ups get reused.
  • The current conversation continues on the new weights, which can read oddly.

B · Live side file needs one test

  1. Each edit becomes a small piece of a side file. The engine calls it an adapter. The 7.2 GB file is never touched.
  2. Bonsai starts the model with the side file loaded but switched off.
  3. A strength slider in the Weights tab turns it on, up, down or off while Bonsai runs. This build of the engine has that control.
  4. A brand-new edit still needs a restart. With edits off, it restores the saved warm-up in a fraction of a second, so the restart takes a few seconds.

Pros

  • Real time: strength changes take effect on the next words, no restart.
  • The original file is never written.
  • Undo is setting the strength to zero.
  • Input-channel edits are exact too.
  • Tiny files, and several edits can be kept and mixed.

Cons

  • Untested with this model's mixed storage. The engine supports side files, but whether they see the mixed or the real form decides how they are built. One test settles it.
  • Only the strength is live. Adding a new edit still restarts the model.
  • What Bonsai already read was read with the old strength. For exact results it re-reads once, about 40 seconds.
  • A little extra work per word for each matrix touched. Too small to guess; measure it in the test.

Fix either way

Four things that apply to both routes.

Never write to the original

bonsai setup checks the original's fingerprint and would report an edited one as damaged. Its fix is to download 7.2 GB again. Edits live in a copy or a side file only.

Saved warm-ups must follow the weights

Today a saved warm-up is matched by the model's file name. A copy edited again under the same name would reuse a warm-up read with older weights. The match needs to include when the file last changed.

The guessing helper was trained on the original

It makes Bonsai write about 14 tokens a second instead of about 10. Edits make its guesses miss more, so Bonsai slows toward the lower number. Measure it after each edit.

Check that the model still works

Hand edits are not training, and most make a model worse. The 28 practice tasks, about 33 minutes, are the check. A shorter set of 5 can be the quick check while experimenting.

Recommendation

Run the side-file test first. It is the only real-time route and it never touches the original. If it fails, build save-and-restart, which needs nothing unknown.

The plan

In order. Each step ends in something you can look at.

  1. Test the side file on this model

    With Bonsai closed and the model stopped, since only one 27B fits in memory: make a side file that turns one row off, start a test server with it, and ask the same question at strength 0 and at strength 1. Compare the answer with what the Weights tab predicts for that row.

    Done when: we know whether side files work here, and which form they see. About 30 minutes.
  2. Add the Edit panel to the Weights tab

    Pick a row, and later a channel. Set ×2, ×0.5 or off, see the change in the Picture before saving, and keep a list with undo. Clicking a channel in the Channels tab fills it in.

    Done when: you can queue and preview edits. Nothing reaches the model yet.
  3. Connect it to the model

    If the test passed, write edits into the side file, load it with Bonsai switched off, and add the live strength slider. If not, write the edited disk clone and add “27B · edited” to /model.

    Done when: an edit changes Bonsai's answers, and undo brings the originals back.
  4. Make the warm-ups follow the weights

    Match saved warm-ups on the weights actually in use: the file's last change, or which side-file edits are on. Setup keeps checking the original only.

    Done when: an edited model never reuses a warm-up from different weights.
  5. Before and after, on one page

    Writing speed with and without each edit, the quick check, and the 28 practice tasks for edits you want to keep. The page goes in the DOCS folder under tests.

    Done when: every kept edit has a measured cost next to it.

What this is based on

Checked on this Mac on 26 September 2026, unless another date is given.

  • The build ignores the model. The bonsai launcher rebuilds only when files in the repo's terminal and models code change. The model file is in ~/.bonsai-code/models, outside the repo.
  • The server loads the file once, memory-mapped. Bonsai starts it with -m and the model path, and the engine maps files by default.
  • Setup fingerprints the original. A file whose SHA-256 differs is reported as damaged, with the advice to delete it and run setup again.
  • Saved warm-ups are matched by file name, engine and helper, not by the file's contents.
  • The engine supports side files, including loading them switched off and changing their strength while running. That comes from this build's own help text. It has not been tried with this model.
  • A disk clone of the model is free. Cloning the 7.2 GB file took 0.00 seconds and changed free space by 0 KB, on APFS. The test clone was then deleted.
  • A restart with new weights takes about 40 seconds. Bonsai's shared instructions are about 2,000 tokens, and the model reads about 55 tokens a second, the average of 87 reads of 2,000–8,000 tokens in the server log. Loading takes about 3 seconds more, recorded 25 September.
  • The weights are stored mixed. In 401 matrices the rows use a Hadamard mix in blocks of 1,024 with fixed sign flips; the word table uses the reverse order. The Weights tab undoes this, and its tests check that against a plain multiply.
  • The helper's effect: about 14 tokens a second writing code with it, about 10 without. The 28 practice tasks took 1,974 seconds. Both recorded 25 September.
  • Free disk: 26 GB of 228 GB.
Where each change would go in the code
  • Edit panel, preview and strength slider: terminal/src/app/weights.html.
  • Saving edits, writing the clone or the side file: the hub server, terminal/src/app/weights.mjs.
  • Starting the model on the copy or with the side file: serverArgs in models/runtime/server.mjs, plus a second model entry for “27B · edited”.
  • Warm-up matching: the key in models/runtime/warmup.mjs.
  • The original's fingerprint: models/runtime/setup.mjs, unchanged, and pointed only at the original.
Why row and channel edits are exact in a side file

Turning row r of a matrix up by a factor k adds (k − 1) times that row to itself: one column vector times one row vector, the smallest possible side-file piece. Turning input channel c up adds (k − 1) times column c, again one column times one row. The Weights tab already decodes both rows and columns in both the mixed and the real form, so it can build either piece. The test in step 1 tells which form the side file receives.

Words used

Weight
One number the model learned. The 27B has about 27 billion.
Row
One output of a matrix. In the feed-forward matrices, a row is one neuron. In the word table, one row per token.
Input channel
One of the 5,120 numbers passed from layer to layer. A column of a matrix reads one channel.
Scale
The number that multiplies each run of 128 stored digits.
Mix
The fixed recipe applied before storing, a Hadamard mix with sign flips. The Weights tab undoes it for the real view.
Side file
A small file of changes the engine adds on top of the model. The engine calls it an adapter.
Warm-up
Bonsai's instructions, already read by the model and saved, so the next start skips reading them.
Helper
A small model that guesses Bonsai's next words so the 27B can check several at once.
