What Gemma is doing while it thinks

Thinking is Gemma writing notes to itself before its real answer. The notes are ordinary text, the same kind of tokens as the answer. The app keeps them apart and does not use them as the reply. Nothing else happens during this time: Gemma doesn't run code or open files. It works the problem out in words, one token at a time.

Below is a real thought, recorded on 28 Sep. We sent test 2's “try a fix” step to your running Gemma again with thinking on, and saved what it wrote. It thought for 765 tokens (2 min 12 s) and stopped by itself, well under the 2,048 cap. The first time it saw this task, in test 2, it used the full 2,048. Thinking length changes from run to run.

What thinking buys you



  

    
What it gives

    
    
      
  • A check before the answer. In step 7 above, Gemma tested its fix against both tests before writing it. On Low, its first guess is the answer.
    • 
      
  • Room to work in steps. It traces values, writes down the rule, then drafts. Low has to get all of that right in one pass.
    • 
      
  • A catch for its own mistakes. If the traced numbers don't match the test, it can change course before writing any code.
    • 
    

  

  

    
What it costs

    
    
      
  • Time. 2 to 3 minutes per code-writing step, against about 14 s on Low.
    • 
      
  • Room in the chat. In chat turns the app keeps the thought, so it fills Gemma's 16k working memory sooner.
    • 
      
  • No guarantee. A careful thought can still be wrong. The real test run is what counts.
    • 
    

  





The catch for Agentic Coder is that it already checks every try. It runs your real tests after each attempt and tries again, up to 8 times. So thinking isn't the only way to catch a mistake. It's competing against simply trying again:



  
One try on Lowabout 20 s

  
One try on Highabout 3 min 10 s

  
8 tries on Lowabout 2 min 40 s




Time for one try comes from test 2's server log: read + write, the test run itself takes under a second. Bars are to scale with each other.



    
  
  1. Where thinking should pay off (expected, not measured): bugs where the error message doesn't show the cause, fixes that touch several places, and cases where quick guesses keep failing the same way. Trying again alone won't find those.
    2. 
  
  2. Where it doesn't: small, clear bugs like test 2. Low gets there first, and the tests catch a bad guess anyway.
    3. 
  
  3. The real answer is the 28-task test (thinking off vs on, same tasks), which hasn't been run yet. Its rule was set in advance: if High passes 2 or more extra tasks, use High for real work. Otherwise, keep Low.
