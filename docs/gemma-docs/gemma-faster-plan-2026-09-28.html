Two things I found while reading the code

1 · The thinking switch sits at the very top of Gemma's prompt. Its template puts a <|think|> mark in the first line when thinking is on. If thinking is flipped between two steps, everything after that mark changes, so the saved reading is lost and Gemma re-reads the whole conversation (about a minute). "Auto" can't just flip the switch on each step. Part 0 below tests a way around this.

2 · "Think less once a file has changed" does nothing on Gemma today. The code drops High to Medium after a change. But Gemma has no Medium: its template ignores the effort word, and only on/off counts. So after a change, every step (run tests, report) still thinks up to 4,096 tokens.

Also already in place, so they are not in this plan: re-reading an unchanged file is pointed back to the earlier read, and long files already show only the lines that match the request.

Part 0 · A quick probe first (about 30 min, real Gemma)

Three questions, each answered by measuring before any building:

  1. Can a step skip thinking without a re-read? Keep the think mark in the prompt, and start the reply with an empty thought (<|channel>thought\n<channel|>, which is what the template writes when thinking is off). If llama-server keeps the saved reading and Gemma just answers, Auto can work step by step.
  2. What does a flip really cost? Time one real on→off switch in the middle of a conversation.
  3. How fast does bge-m3 rank files? Time it on this repo (about 200 code files) and on a small bench project.

If question 1 fails, Auto falls back to once per request: the choice is made when you send the message, and the only re-read happens when it differs from the last one.

Part 2 · Read the right files first

  • New rank.mjs: bge-m3 (already running beside Gemma for memory) turns each code file's name, top-level names and first lines into numbers. They are kept on disk and redone only for files that changed. Each request is matched against them.
  • Step-by-step requests (pages, commands, anything not a fix/change path): the top 2–3 files are read in one go before Gemma's first step, as questions already are. A file named in the request always comes first.
  • The fix/change paths: today, when the request names no file and no test points at one, Gemma picks from the whole file list (a model call). bge-m3 goes first and Gemma picks only when the top matches are close together.
  • A cap, because memory is small: at most ~3,000 tokens read up front (about 20 s of reading) at 16k, more at 32k and above. No ranking in the home folder, or in a project with fewer than 4 code files.
  • Files: new terminal/src/agent/rank.mjs, agent.mjs (prefetch), flows/localize.mjs. Tests: the right file ranks first on 5 bench tasks, cache reuse, the cap, skipped in home.

What could go wrong

  • A "question" that is really hard gets no thinking. Answers might get shallower. The fix: say "think" in the request, or the rule gets moved.
  • Ranking picks the wrong files. That wastes up to ~20 s of reading. The cap keeps it small, and the bench shows it.
  • More questions to you mid-task (asks after 2 repeats or 3 errors, not stops). That is the trade you picked.
  • Part 0 fails. Auto becomes once per request. That is still the big win for pages and questions, but a fix keeps thinking through its tests and report steps.
  • One run each is noisy. Gemma's replies vary, so a single slow task isn't proof.
