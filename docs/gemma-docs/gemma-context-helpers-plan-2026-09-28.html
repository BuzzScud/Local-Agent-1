Context helpers for Gemma: the plan

The idea is to give Gemma the right things before it starts, so it needs fewer steps to go and find them. There are four helpers: files you name, test results and recent changes, code found by meaning, and a light syntax check. Together they may add at most about 6,000 tokens to a request. Each one gets its own switch, so the before/after bench can measure it. Nothing is built yet. Your app and the repo are unchanged.

Why this can pay

Gemma reads about ten times faster than it writes. Each step it takes means writing (and on High, thinking), and each thing pasted in only means reading.

WhatMeasured (Gemma's server log)
Reading pasted text112–125 tokens a second, so 1,000 tokens ≈ 8–9 s
Writing11–12 tokens a second
One step, short189 tokens written = 16 s
One step with High thinking1,737 tokens = 2½ min; 5,533 tokens = 8 min
Your settings nowHigh effort, thinking up to 8,192, 256k memory. Room isn't the problem; reading time is.
The trade: a full 6k paste costs about 50 s of reading. On High it pays for itself if it saves one step. If it pastes the wrong thing, those seconds are wasted, so 6k is a ceiling, not a target: each helper only adds what clears its own bar.

What's there today

Agentic Coder has two ways of working. A focused path handles clear fix / change / rename requests: the program reads the files and runs the tests itself, and Gemma only writes the change. Everything else goes step by step: Gemma picks every Read, Search and test run itself.

Two things I found while reading

  1. notes.html won't move. It runs from your home folder and makes a new file. The home folder has no project map, no git and no tests, and the file doesn't exist yet. None of the four helpers fire, so it stays in the bench as the "no slowdown" check, as you picked.
  2. All four code tasks take the focused path. On the earlier 27B runs, task 19 went Plan → Read ×3 → Test → Ask → Update ×3 → Bash. The program made those Reads, not the model. So helpers that only feed the step-by-step loop would barely touch these tasks. The plan handles this two ways:
    • the helpers also feed the focused path (which file it picks, and the check after each change);
    • the bench runs each code task twice, once as your app does it and once with the focused path off, so we see the step-by-step case where Gemma makes every Read itself.
    "Steps" on a focused path include the program's own reads, so the bench also counts Gemma's own calls, tokens written, and minutes.

  3. For each run, record Gemma's own calls, tokens written, minutes, pass/fail, and how many helper tokens came along.
  4. Add notes.html as bench task 29, with the exact prompt. It runs in a throwaway home folder, so your real Desktop is never touched. The check: the file exists, has the charset, and the page opens with no errors (the app's own page check).
  5. Run the "before" set with the helpers off: notes.html once, and tasks 2, 22, 19 and 26 once on each path. That's 9 runs at High.

Part B · Test results and recent changes ~1½ h

  1. Tests: when the request is a fix, or mentions failing, broken, error or tests, the test command runs once before Gemma's first step (60 s cap). The failing test names and first error lines come along (≤1.5k tokens) as a pretend test run, so Gemma treats it as its own. If everything passes, it's one line: "Tests: 14 pass".
  2. Recent changes: if the project has uncommitted changes, the changed lines come along, biggest files cut first, with a "… and N more files" line. This shares the 1.5k with the tests.
  3. It all goes into the request, not the start-up text, so Gemma's saved reading of the start-up text is kept.
  4. Focused path: the fix path already runs tests. The recent changes are added to what its "is this clear?" question sees, which helps task 22 ("fix the bug" while the tests pass).
  5. Guards: nothing in the home folder, nothing without a test command, and a hung test run is stopped at 60 s with a note saying so.

Done when: in the step-by-step runs of tasks 2 and 22, Gemma no longer starts by running the tests itself.

Part C · Code found by meaning (RAG) ~3 h

  1. Each code file is split into its named parts (functions, classes). The existing outline code already does this split. bge-m3, the same model that serves your memory, turns each part into numbers.
  2. The results are saved per project next to the project map, and keyed the same way (file size and time), so only changed files are redone.
  3. For each request, the request is turned into numbers once and shared with memory recall. That's recall fix 3, which was never built.
  4. The 3–5 closest parts above the bar come along (≤1.5k tokens), each as a pretend Read with its line numbers. The bar starts at memory's 0.56 and gets tuned on the bench.
  5. Focused path: the file list it picks from gets ranked by meaning and words, not by words alone. This is Part 2 of the earlier "feel faster" plan ("read the right files first"), so it gets built once, here.
  6. Guards:
    • No index in the home folder.
    • Minified and huge files are skipped.
    • The first index of a project builds in the background, and a request never waits for it.
    • If bge-m3 is not up, ranking works by words as today.

Done when: in the step-by-step run of task 26, the folder walker in fs.mjs arrives without a Search. On the focused path, it no longer reads scratch.mjs (an unneeded file the 27B read).

Part D · Light language checks ~1 h

  1. After every Edit or Write, on both paths, the file gets a syntax check:
    • JS files: node --check
    • JSX and TS: bun build --no-bundle (bun is already on the Mac)
    • Python: py_compile
    • JSON: parsed
    An error comes back in the Edit's own reply ("Saved. Line 42: Unexpected token"), so it doesn't cost a step.
  2. "Where is it, who uses it": for names in the request that the project map knows, one short line lists the file that defines each name and the files that import it (≤0.5k tokens).
  3. Not built A full language server (typescript-language-server, pyright). That only happens if the multi-file tasks still take many steps after this round.

What could go wrong

  • The wrong thing gets pasted. That costs about 8 s per 1,000 tokens for nothing, and on a short task the helpers could make it slower. The bars, the ceiling and the notes.html check are there to catch this.
  • Tests run up front on a slow suite. That adds time before Gemma starts. It's capped at 60 s and only happens on fix-type requests.
  • The first index of a big project takes a while. It runs in the background and never holds up a request.
  • The bench shares Gemma with your app. If you use coding during a run, both slow down (we saw 12 → 8 tokens a second once) and the minutes get skewed. It's best to run the bench when you're not using it.
  • One run per task is noisy. A single lucky or unlucky run can swing the minutes. If the result is close, the page will say so rather than claim a win.
