What Bonsai 2 27B is

PrismML's newest model, released 17 Sep 2026. It is a squeezed-down copy of Qwen3.8-27B, a model about 3× the size of the one the 8B came from. Like the 8B, it stores every weight as −1, 0 or +1. That shrinks it from 54 GB to 7.2 GB and keeps 98.2% of the full-size model's test scores. It can also look at pictures and handle conversations 4× longer.

Inside: why 3× bigger isn't 3× hungrier

Each block below is one layer, a step the text passes through. More layers and more weights hold more knowledge but take longer. The difference is how the layers remember the conversation.

Ternary Bonsai 8B36 layers; every one looks back over the whole conversation
Bonsai 2 27B64 layers; only 1 in 4 looks back over everything
Looks back over every earlier token, so it needs memory for each one ("full attention") Keeps a fixed-size running summary instead ("linear attention")

Memory to hold a 32,000-token conversation (GB)

Only 16 of the 27B's layers need room per token, and each needs less. The result: 35 KB per token against the 8B's 78 KB. So the bigger model holds a long conversation in half the memory. Its limit is 262,144 tokens against the 8B's 65,536. On your Mac, though, the graphics-memory limit stops it at about 60,000 (est. from tonight's measured memory).

How both squeeze their weights

Normal model, 16 bits each:
0.0132 · −0.0207 · 0.0009 · 0.0188 · −0.0151 …
Bonsai, about 2 bits each:
+1 · −1 · 0 · +1 · −1 … × 0.017

Made-up numbers to show the idea. Each weight becomes −1, 0 or +1, and every 128 weights share one scale (the × 0.017). This is how 16.4 GB becomes 2.18 GB, and 53.8 GB becomes 7.21 GB.

Real outputs from tonight's test

Run through the engine with Bonsai Code's own settings: 32k memory, 8-bit cache, thinking off unless noted. Copied as the model wrote them.

1 · A focused job · 49 s

Given Bonsai Code's server.mjs (7 KB): "Add an exported function stopAll() that stops each live server in the registry and deletes its registry file."

export async function stopAll() {
  mkdirSync(REG_DIR, { recursive: true });
  for (const f of readdirSync(REG_DIR)) {
    const p = join(REG_DIR, f);
    let e;
    try { e = JSON.parse(readFileSync(p, 'utf8')); } catch { rmSync(p, { force: true }); continue; }
    if (!alive(e.pid)) { rmSync(p, { force: true }); continue; }
    try { process.kill(e.pid, 'SIGTERM'); } catch {}
    rmSync(p, { force: true });
  }
}

Correct on the first try. It reuses the file's own helpers (REG_DIR, alive, rmSync) and even skips broken registry files, the way the file already does.

2 · A tool call · 8 s

"What does export.mjs print? Use the Read tool to look at it first."

Read({"path":"export.mjs"})

A proper tool call. The engine understood the 27B's own tool-call format, so Bonsai Code gets a normal call it can run. PrismML's known problem (broken or repeating calls) didn't show up here.

3 · A forced-JSON reply · 2 s

"Sort this request into one kind: rename getUser to fetchUser everywhere." The reply is forced into the shape Bonsai Code's request sorter uses.

{
  "kind": "rename"
}

Right answer, valid shape.

4 · Thinking on "medium" · 35 s

"Write a JavaScript function median(nums)… average the two middle values for even lengths."

function median(nums) {
  const sorted = [...nums].sort((a, b) => a - b);
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2;
}

Correct. It thought for about 200 tokens and wrote 319 in all. That's short: PrismML warns its default "xhigh" setting can think far longer.

What it would mean for Bonsai Code

PartWith the 27BWhy

Bottom line. Measured, the 27B does what its scores promised: the right code on the first try, a clean tool call, and short thinking. It is 3.5–4× slower, which you've said is fine. Memory is the real cost, about 10 GB, so it works best with the desk servers stopped. Next is teaching Bonsai Code to use it. Until then the installed bonsai command can't start, because the 8B is gone.
