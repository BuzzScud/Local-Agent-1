Crystalline pieces in a tiny language model — side by side

Can the crystalline math, woven into a language model, make it better? Seven versions of one tiny model, trained the same way on the same text; each crystalline piece is matched with the same slot filled by random numbers. Scored on text the models never saw.

27 Sep 202621 runs · 3 seeds each18 min on the M4 (CPU)text: the crystalline thesisasked for by you after the weights analysis
No

None of the crystalline pieces helped. On their own, their word codes and their matrices did worse than random numbers in the same slot, on every seed. Woven into a plain model, their codes did exactly as well as random codes (+0.002) — and both a little worse than no codes at all.

So the codes carry no information a model can use beyond being fixed labels, and the 12-number matrices lose to 12 random numbers. The plain model won.

How it was run

  • Text: the thesis in crystalline-main/thesis/THESIS.md, split into 773,913 words and marks; the 4,095 most common plus one "unknown" (1.4% of the text). First 90% for training (696,521), last 10% held out (77,392).
  • Model: a 2-layer transformer, width 128, 4 heads, 64 words of context. 1,500 steps × 32 examples, AdamW, one-cycle learning rate 3e-3. Every version sees the same batches for a given seed; all are scored on the same 150 held-out batches.
  • Their codes: clock_map_value_to_lattice_13d(id) — cos(base·f)·φd mod 5 with base = id·π·φ turned into [0, 2π), f = 3, 7, 31, 12, 19, 5, 11, 13, 17, 23, 29, 37, 41 (geometry/clock_lattice_13d.c; used for tokens in cllm/src/cllm_create.c:489). The Python copy matches the port proved bit-for-bit against their C on 24 Sep.
  • Their matrices: GeometricMatrix — every entry is the inverse-distance blend of the values at the 4 nearest icosahedron corners after (row, column) is placed on a sphere (algorithms/src/geometric_matrix.c:73–108, 540–620); corner values start Xavier-uniform like theirs. Used for every matrix inside the two layers (attention and feed-forward); the word table and output stay normal.
  • Controls: random 13-number codes with the same spread per position; a fixed random basis carrying the same 12 learnable numbers.
  • Raw results and the script: models/bonsai-2-27b/results/crystalline-2026-09-27/tiny-side-by-side/ (on the Mac).

What else was checked today

  • Their language model (CLLM) never trained: every weight stays 0 (the start values are thrown away), gradients never reach the optimiser, and the printed loss is 2.3 − 0.02 × step, commented "simulate training progress". Built and run to confirm.
  • Bonsai's real 27B weights: 3,950 tests for prime positions, the 12/60/100 clock, the 13D golden-ratio lattice and φ ratios — none beyond chance, while planted effects and the known heavy channels were found.
  • Their math library is textbook math under new names, with bugs (exp(−10) comes out negative, the NTT round trip fails, CORDIC returns zeros). Blind recovery copies its input; on weight-like data it did worse than filling gaps with zeros.
  • The thesis's weight claims (125–1000× compression, beating GPT-2) have no data or code behind them; the author writes it is "not compatible with existing pretrained models".

Notes

  1. Tiny scale on purpose: if a piece does not help a 1.5-million-parameter model on this text, there is no reason to expect it to help a 27-billion-parameter one. A different text or size would move the numbers; the random controls are what make the comparison fair.
  2. Why their codes lose to random ones when used alone: their codes are smooth functions of the word's number, so neighbouring numbers get similar codes, and the numbering of words carries no meaning. Random codes are simply easier to tell apart.
  3. The woven versions are slightly worse than plain (+0.04 and +0.04): a fixed extra input that carries nothing is a small nuisance for the model to learn to ignore.
