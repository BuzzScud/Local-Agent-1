Bonsai's memory: what was built and what it does

Built on 26 Sep 2026 in a copy of the repo of its own, not yet committed. Bonsai now saves what it learns on its own, keeps it as small files, and brings a fact back when a request fits it. Every number here was measured on this Mac with Bonsai 2 27B; the highlighted cell in a row is the better one.

What the memory itself did: in the 3 plain questions a saved fact was used the second time, and they went from 9 steps and 54 s to 3 steps and 30 s: Bonsai answered from what it knew and read one file to make sure. The large gain on the big-project question is not the memory's: its first run got stuck on five failed commands in a row (a weakness known from earlier rounds), its second run used no saved fact and simply went better.

2 Time on a practice task moves from run to run without any change to Bonsai: task 1 took 138 s in the run without memory, and 79 s, 82 s and 139 s in three runs tonight. A difference of a few seconds between a first and a second run is inside that noise. The count of steps does not move that way, which is why it is shown beside the time.

Why code tasks gain nothing: they run on Bonsai's focused paths (fix, change), which take the same fixed steps whatever the memory holds. A fact such as "averaging the two middle values fixed the median bug" reaches the model, but the path still writes its tries and runs the tests.

What was built

PartWhat it doesChecked by
The storeterminal/src/agent/facts.mjsOne small file per fact, an index, a folder for facts taken out of use, a log, undo. Your two rules are saved at the first start. A key or a password is refused.9 unit tests
Bringing facts backagent/recall.mjs · models/bge-m3By meaning with BGE-M3, by words without it. The fact is written into the request, so nothing already read is read again.9 unit tests, the 30-request check
Saving on its ownagent/lessons.mjs · app/autosave.mjsA little after a task and when you quit. At most 5 facts. A fact the turns do not bear out, or one naming a file that is not there, is refused.8 unit tests, 3 tests of the real app
Trustagent/agent.mjs+1 when the task passed its check, −1 when it failed or Bonsai got stuck, −2 when you corrected or stopped it. At −3 a fact goes out of use.unit tests5
First use, recipes, tidyingagent/lessons.mjs · facts.mjsEarlier conversations are read once. The steps of a job done twice are saved. Repeats merge; old and orphaned facts go out of use.unit tests5
Seeing it/memory · the hub's Memory tabBoth memories in the window; every fact in the browser, to edit, pin, take out or bring back. Only the hub's own page may change the memory.3 unit tests, the page in two browsers at three widths
The night reviewapp/review.mjsReads the day's conversations again while the Mac is idle. Not scheduled: bonsai memory-review --install does that, and it is yours to run.4 unit tests5

5 Trust, tidying, undo, the first-use reading and the night review are covered by unit tests with a stand-in model (they do what they are built to do). Whether they make Bonsai better in daily use can only be seen after days of real use.

3 A save costs model time even when there is nothing to save: 13 s on average for the saves that added nothing. You do not wait for it, but the Mac works for it. Skipping the save when a turn only repeated what the memory holds would remove most of that.

Not done, and corrections

Not built: the harness changes of the plan (the trim, the repeated read, acting as soon as the cause is named). They were not part of this go-ahead.

Only on the fix path: the facts brought back go into the prompts of the fix path. The change and several-files paths do not read them yet.

A correction to the plan page: it said the model already stays loaded for a while after you quit. A plain quit stopped it. Now a quit with something left to save keeps the model until the save is done (about 15 s), then stops it.

Not committed: the work is in ~/worktrees/bonsai-memory on the branch memory-v2. Main has moved since (the /morning command), in four files this work changed too, so committing includes a merge and a new run of the tests.

A test runner's fault, fixed: the first run of the questions was marked failed on every task because the runner did not write the answer file their checks read. It was run again; only the second run is shown.

Where the numbers come from

  • The recall check: node models/evals/bench/memory/recall.mjs → models/bge-m3/results/; the other matchers: models/evals/dev/experiments/julia-recall/ → models/bge-m3/results/matchers/.
  • The second time: node models/evals/bench/memory/second-time.mjs [--only 5,6,7,22,25,26] → models/bonsai-2-27b/results/memory/.
  • The 28 tasks: node models/evals/bench/run.mjs --think off --memory → models/bonsai-2-27b/results/runs/.
  • Every run is in the test record (/tests). This page: node models/evals/reports/report-memory.mjs.
