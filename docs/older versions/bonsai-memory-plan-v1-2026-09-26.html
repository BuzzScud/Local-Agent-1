A memory that makes Bonsai better each time you use it

Today Bonsai forgets everything when you close the window, unless you type "update memory". This plan makes it save what it learns on its own, keep it tidy, and bring back only the facts that fit the request in front of it.

Based on your six answers from tonight and on what the code does today. Every number marked "measured" comes from this Mac; every number marked "estimate" is checked during the build.

How it works

Four steps. The first two happen after a task, the last two before the next one.

1 · After a task
Collect

Bonsai gathers what happened: your request, your corrections, what it changed, which tries passed or failed, and whether it got stuck.

2 · In the background
Save

The model turns that into at most 5 short facts. If you send a new request, the save steps aside and finishes later.

3 · On disk
Store

Each fact is its own small file with its kind, its key words, and where it came from. The index gets one line per fact.

4 · Next request
Recall

The request's words are matched against the facts' key words. Matching facts travel with the request. No model call is needed for this.

Why the facts travel with the request: Bonsai saves the model's reading of its fixed instructions to disk, so a start takes a fraction of a second. If memory sat inside those instructions, every new fact would throw that saved reading away. Placed after them, memory costs nothing at start.

What a saved fact looks like

Plain text files you can open, edit or delete yourself. These are examples, not real saved facts.

What it learns

Four kinds of fact. Each one comes from something Bonsai can see for itself, not from a guess.

How you like to work

Saved in your own memory, used in every project.

"Explain what you are going to do in plain language before doing it."
Comes from: what you say, and the corrections you give after an answer.

Project facts

Saved in the project's memory.

"The rules for fixing bugs are in terminal/rules/bug-fixing.md."
Comes from: files it read and commands that ran without error.

What worked and what failed

Saved in the project's memory, with the check that proved it.

"Failed: raising the menu's z-index. Worked: lowering the legend's."
Comes from: the result of each try and of the project's tests.

Its own mistakes

Saved in your own memory when it is about how Bonsai works, in the project's when it is about the code.

"Read the same file four times and stopped. Next time: ask, do not re-read."
Comes from: a loop, a stop at the time limit, or you pressing esc.

Build steps

In this order. Each step is tested before the next starts, and the 247 existing tests must keep passing.

  1. The store

    Facts as small files, the index, the retired folder and the log. Your two rules go in as the first facts. An existing notes file is carried over line by line.

    Files: terminal/src/agent/memory.mjs, new tests. No model needed.
  2. Recall

    The index is placed after the fixed instructions. Matching facts go with the request, the way bug steps and your math notes already do.

    Files: agent/prompt.mjs, agent/agent.mjs. Test: the right fact arrives for the right request.
  3. Saving on its own

    A save starts when a task ends and when you quit. It runs on the model's second slot, steps aside when you type, and finishes after the window closes.

    Files: agent/agent.mjs, app/App.jsx, headless.mjs. Here the real save time is measured.
  4. Learning from results

    Each task leaves a short record: tries passed and failed, your corrections, loops, interruptions. The save reads that record, so lessons come from what happened.

    Files: agent/agent.mjs, flows/.
  5. Upkeep and undo

    Merge, replace, retire, the log, and the /memory command with undo. The Help page gets the new command.

    Files: agent/memory.mjs, app/commands.mjs, app/App.jsx, app/help.mjs.
  6. Measure

    The checks in the next section, run on the real model, written to the test record, with a results page in the DOCS folder.

    Files: a new runner under models/evals/bench/, reached through terminal/index.mjs.

A correction: earlier I said a save costs about 20 to 40 seconds of model time. With the reading of a long conversation counted, 20 to 60 is the honest estimate. Bonsai reads about 55 tokens a second and writes about 10 (both measured). Step 3 replaces the estimate with a measured number.

Limits you should know

  • The model does not grow. A harder problem than the model can solve stays too hard. Memory saves it from repeating work and repeating mistakes.
  • The gain shows in projects you return to. In a folder opened once, there is nothing to remember yet.
  • A small model can save a poor fact. That is why each save is limited to 5 facts, each must name where it came from, and the fifth check reads them.
  • Only one model fits in memory on this Mac. A save shares the model with your next request, which is why it steps aside when you type.
  • A wrong fact can mislead. Facts about code are checked against the files before they are recalled. Facts about you are only replaced by what you say later.

Small picks I made for you

You did not have to decide these. Say so if you want any of them different.

  • Your own memory lives in ~/.bonsai/memory/, a project's in .bonsai/memory/ inside the project.
  • A save may finish after the window closes. The model already stays loaded for a while after you quit.
  • A Memory tab in the hub is left for a later round. /memory in the window comes now.
  • The old "update memory" words keep working and save at once.
  • A setting turns saving on its own off, for a project or everywhere.

Words

Fact
One short thing worth remembering, in its own file.
Index
A short list with one line per fact. It is the only part of memory always loaded.
Recall
Bringing a saved fact back for a request that matches it.
Retire
Move a fact out of use without deleting it, so it can be brought back.
Slot
A place in the model server for one conversation. Bonsai has two: one for you, one for side work such as a save.
Token
A piece of a word. The model reads and writes in tokens.
