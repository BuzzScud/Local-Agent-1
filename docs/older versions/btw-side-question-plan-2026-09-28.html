How it works

  1. Three lanes on one model. Lane 0 holds the conversation. Lane 1 does the side jobs it does today: sorting a request, memory saves, /morning. Lane 2 is new and only answers /btw, so a side question never waits behind a memory save.
  2. A short summary goes with your question. It covers the request, the to-do list, the steps so far with outputs cut short, what is running and for how long, and the last thing it said. That's about 1–2k tokens, read in roughly 8–16 s at the model's recorded reading speed of about 127 tokens/s. Re-reading the whole conversation would take minutes and might not fit in memory.
  3. One answer, no tools, no thinking. The answer is capped at about 400 tokens. Its instructions ask for a few plain sentences, and for it to say "a guess" when it guesses, which it will for times.
  4. The main job keeps going. Both lanes run at the same time. The main job writes somewhat slower while the answer is being written. By how much hasn't been measured yet; that is step 1 of the build.
  5. The main conversation never sees it unless you press f. Every side thread is also kept in the session file, and /btw typed alone reopens the last one.

What the side question sees

An example of the summary, with made-up task details and the real layout:

You answer a quick side question while Agentic Coder keeps working. You cannot use tools or change anything. Answer in a few short sentences. If you have to guess (times especially), say it is a guess. The work so far (4m 12s): - Request: "fix the failing date test in src/when.mjs" - Plan: 1 read the test ✓ 2 find the cause ✓ 3 fix it ✓ 4 run the tests (now) 5 report - Steps: Read(test/when.test.mjs) · Grep(parseDay) · Read(src/when.mjs) · Edit(src/when.mjs, 3 lines) · Bash(bun test), running 48s - Last said: "The day was read in UTC; I switched it to local." - Earlier here: 2 requests (their first lines only) Question: eta?

It's built from what's already on your screen and the agent's to-do list, then cut to fit the room left.

The room check

All three lanes share one memory pool. The server already clears a lane that is sitting idle when the pool gets full. But if two busy lanes overflow the pool, the main job's request fails. So before sending, /btw works out the room left: the pool, minus the conversation, minus the room kept for the main job's reply, minus lane 1 if it's busy (it asks the server which lanes are busy). It cuts the summary to fit. If fewer than about 600 tokens are left, it shows panel 5 instead of sending.

Keys, and what wins when two things happen

EscCloses the panel (and stops the side answer if it is still writing). It never stops the main job. Once the panel is closed, Esc works as it does today.
ctrl+cCloses the panel first; the next ctrl+c works as it does today.
↑/↓ · c · f · rScroll, copy the answer, send it to the main job, ask a follow-up. Other keys do nothing while the answer is shown: press Esc to type to the main job.
The main job asks you somethingIts question wins: an "Allow Bash?" or a question you type an answer to takes the panel's place. The side answer keeps writing, a line says "side answer ready · shows after you answer", and the panel comes back after you answer.
"Remember for next time?"The memory's Save / Skip menu waits until the panel is closed, as it already waits while you type.
The main job finishesIts "Worked for …" line prints above as usual and a queued message sends. The panel stays open.
f, send to mainThe side question and answer ride along with your next message to the main job, the same way !command output does today. A note says so. Nothing interrupts the current step.
Model still starting"The model is still starting; ask again in a moment." Nothing is queued.
Fewer lanesA model still loaded from before this change (2 lanes) or shared with another window: /btw uses lane 1 and waits behind a memory save if one is running. A server given with --url and 1 lane: /btw works only when idle and says so while busy.
Small windowThe panel is capped to the rows left, and the answer scrolls inside it (your "displays correctly at all times" rule). Too small: the usual "window too small" screen.
Quit, /clear, /resumeQuitting stops a side answer. The others can't be typed while the panel is open (the prompt box is hidden); after Esc they work as today.

What we don't know yet

unknownHow much the main job slows while a side answer is written. Step 1 measures it before anything else is built.
costThe extra 0.72 GB can move a Mac that is on the edge from 32k down to 16k. Right now this Mac has 2.5 GB free and would start at 16k either way.
quality"eta?" is a guess for a small model. The summary gives it the elapsed time, the step it's on out of the total, and the tries, and it is told to label guesses. It can't know how long a test will run.
repoThe repo is busy. The rename work is still uncommitted (about 120 files), and another session changed AGENTS.md at 12:33 while this plan was written. Building in the main tree mixes with both, so a separate worktree may be cleaner.
Not in this plan: giving /btw the whole conversation. This server version can reload a lane's older state from RAM, so a later round could try it, but a big conversation would still take minutes to read. You picked the short summary.
