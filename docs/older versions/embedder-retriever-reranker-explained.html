Embedder, retriever, reranker

An LLM can only use what is in its prompt. It cannot see your whole project at once. When the answer sits somewhere in a big pile (thousands of functions, hundreds of notes), these three parts choose the few pieces worth showing it.

Embedder
Turns text into a meaning address

The address is a list of numbers. Texts that mean similar things get addresses close together, even if they use different words.

Speedvery fast
Retriever
Finds the closest addresses

It compares the question's address with every stored one and keeps a short list, say the top 30. It is quick but rough.

Speedvery fast
Reranker
Reads the short list carefully

It reads the question and each piece together, scores how well each one answers it, and puts the best few on top.

Speedslower
The everyday picture: a library
  • Embedder: a librarian who shelves every book by topic, so books about the same thing sit side by side. Your question gets a spot on the shelf too.
  • Retriever: you walk to your question's spot and grab the 30 nearest books. That's fast, but some of them only sit nearby by accident.
  • Reranker: you sit down, skim each of those 30 with your question in mind, and keep the best 5.
  • The LLM: reads those 5 and writes the answer.

What a “meaning address” looks like

Why two steps? Why not only the careful one?

The difference comes down to one thing. The embedder reads the question and each piece separately. The reranker reads them together.

  1. Reading separately means every piece's address can be made ahead of time. When you ask something, only your question is new. Comparing it with 10,000 saved addresses is simple math and takes milliseconds.
  2. Reading together gives much sharper judgement. The reranker can notice that “after a password reset” is the important part of the question. But nothing can be prepared ahead, so every piece costs a full read when you ask.
  3. Rough numbers: running the reranker on all 10,000 pieces would take minutes. Letting the retriever cut them to 30 first takes milliseconds, and the reranker then finishes the 30 in under a second.

The retriever is a wide net: fast and rough. The reranker is a fine sieve: slow and sharp. Used together, the search is both fast and sharp.

An example (made-up numbers)

The question is “Why does sign-in fail after a password reset?”. Only the top 3 pieces go to the LLM.

Without the reranker, the LLM gets the screen, the help page and checkPassword(). It never sees the two pieces where the bug most likely lives. The retriever was fooled because “sign-in” and “login” appear everywhere. The reranker read the question and the code together and caught “after a reset”.

In a coding agent like Agentic Coder

The pile here is your project. The pieces are functions and file parts, plus Agentic Coder's memory notes.

  1. When a project opens, the embedder gives every function an address and saves them. Next time, only changed files get new ones.
  2. You type a request, and the request gets an address too.
  3. The retriever pulls out the 20 or 30 closest functions.
  4. A reranker would put them in order with your request in mind.
  5. The best few go into Gemma's prompt before it takes its first step.
Why this matters more for a small local model Gemma's working memory is small, and every extra piece costs reading time. One wrong file wastes tokens and seconds, and it can send Gemma down the wrong path. Better picks mean fewer steps.
The coding twist: exact names Meaning search is good at questions like “where do we handle sign-in?”. It is bad at exact strings such as a function name, an error message, or ERR_TOKEN_EXPIRED. Plain word search (like grep) nails those. Good code tools use both. Word search finds exact names, meaning search finds ideas, and a reranker merges the two lists into one order. This is called hybrid search.

What Agentic Coder already has

EmbedderHave

BGE-M3 runs on your Mac and is about 600 MB. Two things use it: Oracle (code search by meaning) and memory (finding the right note for a request).

RetrieverHave

Oracle keeps the closest functions above a cut-off score. “Read first” reads up to 3 of the closest files whole. Scout reads the files you name. Gemma can also search by words itself.

RerankerNot built

The 26 Sep plan had one idea: the embedder orders, then the big model checks the top 5. It was never run.

The 26 Sep matching test already shows the trade-off. It used the same 20 notes and 30 requests. BGE-M3 got 23 right and 1 wrong in 17 ms. The 27B model, picking by itself, got 25 right and 1 wrong in 3.5 s. The careful reader was better but about 200 times slower. That is exactly why a reranker only looks at a short list.

In general: where you meet these

  1. “Chat with your files” tools and company help bots use an embedder, a retriever and often a reranker. The whole recipe is called RAG: look things up first, then write the answer.
  2. Web search engines use the same two-step idea at huge scale. A fast first pass covers billions of pages, then heavier rankers sort the top ones.
  3. Code editors like Cursor index your codebase with an embedder, so the chat can find the relevant code.
  4. Claude Code, the tool writing this page, uses no embedder at all. It searches with plain word search and file lists, reads what it finds, and decides what matters. The big model is its own retriever and reranker. That works well with a strong model but takes more steps and tokens. With a smaller local model like Gemma, an embedder and a reranker can do part of that work for it, cheaply.
