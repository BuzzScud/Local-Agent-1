The Opus 5.5 and Fable 5.1 harness version 2

The harness is everything around the model. It sets up a sealed computer, hands over the task, checks every turn for safety, runs the tools the model asks for, keeps the conversation from overflowing, and grades the result. This page is drawn from the two system cards: Fable 5.1 (1 Sep 2026) and Opus 5.5 (22 Sep 2026).

    3 · The safety net in detail

    Classifiers are small checking models. They read every turn before the model answers. Here's what each one looks for and what happens when it trips.

    CheckWhat it looks forFable 5.1Opus 5.5
    Cyberhelp with hacking and attacksOpus 4.8 answers the turnOpus 4.8 answers the turn (the card says it's set stricter for now, because Opus 5.5's cyber skill is close to Mythos 5.1)
    Biologyresearch biology that could help with bio or chem weaponsOpus 5 answersOpus 5 answers (same checks as Fable 5 and 5.1)
    AI researcha narrow set of frontier-AI work, e.g. writing kernels for certain AI chipsOpus 5 answersOpus 5 answers
    Weaponsconventional weapons and high-yield explosiveshard blockhard block, no backup
    Copying the modele.g. trying to pull out its hidden reasoningnot listed1hard block, no backup

    How it behaves

    1. The check reads the turn before the model answers.
    2. If nothing is flagged, the model answers as normal.
    3. If it's flagged, the backup model answers that one turn and the conversation carries on. Some checks end the conversation instead.
    4. Blocks are visible. The card says they never quietly change an answer.
    5. In Anthropic's own apps the backup happens automatically. On the API, a developer has to opt in.

    How often it happened in tests

    1. Terminal-Bench 4.0, Opus 5.5: the backup answered 2.5% of requests, touching 10% of tries.
    2. Terminal-Bench-Science, Opus 5.5: 3.9% of requests, 5% of tries.
    3. Toolathlon, Opus 5.5: 1 of 324 tries was stopped by the safety checks and counted as a fail.
    4. Team runs, Fable 5.1: 72% of runs had at least one backup turn, but that was under 1% of all turns.

    Some tests turn the checks off on purpose to measure the raw model. The cyber tests do (with the escape watcher still on), and so do the math tests. The prompt-injection test compares no guard against "auto mode", which adds injection probes and a tool-call checker.

    5 · Teams: the two setups both cards tested

    Instead of one agent, several copies of the model work on the same task at once. Both cards used the same two setups on ProgramBench, where the job is to rebuild a program from only its compiled file and its manual.

    A · Team of five, step by step

    1. The harness starts five copies at once. Each gets the full task and the same tools.
    2. On ProgramBench each has its own copy of the code. On DRACO they share one computer's files.
    3. Nobody hands out the work. The five split it up themselves.
    4. Send Message reaches one or more teammates and shows up right after the reader's next tool result. Wait for Message pauses an agent until something arrives.
    5. They trade code through Git.
    6. End: on ProgramBench, when all five are done, and the main branch is graded. On DRACO one agent is the lead, and the run ends when it finishes. The report as it stands then is graded.

    B · Lead + helpers, step by step

    1. Only the lead starts. It has the task and the task tools.
    2. The lead creates a helper and writes its instructions. The tool returns right away and doesn't wait for the helper.
    3. The helper sees only those instructions, never the original task.
    4. Helpers work at the same time and can message the lead or other helpers.
    5. When a helper finishes, its answer arrives at the lead as a message. The helper then waits until the lead gives it new work.
    6. The lead can check each helper's status and stop helpers. There's no cap on how many.

    Small difference between the cards: in the Opus 5.5 card only the lead can Wait for Message, and status includes "queued". In the Fable 5.1 card helpers can Wait too, and stopping a helper frees a slot.

    Results · Fable 5.1

    The team of five reached a score of 0.6 about 2× sooner than one agent.

    Lead + helpers was faster than one agent and finished with the highest final score.

    Each agent had a shell and up to 1M tokens. The safety checks were on, with Opus 5 as the backup.

    Results · Opus 5.5

    The team of five reached 0.6 about 2.7× sooner. Lead + helpers landed in between.

    The single agent got 20M tokens and summarizing, so the teams' extra tokens weren't an unfair edge.

    Run on a slightly different version of Opus 5.5 with similar performance.2

    The time-pressure test (Opus 5.5 card, DRACO research reports)

    1. Run each research task with one agent and note how long it takes (13 to 71 minutes).
    2. Pressure: tell the teams speed matters and show the elapsed time after every step.
    3. Budget: instead, give a fixed time window of 1×, 0.75×, 0.5× or 0.25× the single agent's time, shown next to the elapsed time.
    4. Compare score against time. Each point is the average of two runs, all at max effort.

    What it found

    1. With no pressure, teams were slower than one agent on these short tasks, because talking to each other takes time.
    2. With half the time (0.5×), the team of five matched or beat one agent's score about 2.8× faster.
    3. With very little time, lead + helpers mostly stopped creating helpers and worked like a single agent. The team of five, already started, kept working in parallel.
    4. Lowering effort means less work gets done. A time budget keeps the work and spreads it across agents.

    6 · New in the Opus 5.5 card: big teams Opus 5.5 only

    1 to 100 agentsone named lead, the rest helpers, all starting together
    24 hoursthey check the clock themselves and plan around it
    One shared machineLinux, no internet, one Git repo that gets graded
    Same tools eacha shell, a file editor, Send and Wait for message

    Step by step

    1. The harness starts a team of N agents together (N from 1 to 100): one lead and N−1 helpers. All of them get the full task.
    2. They all work on one shared Linux machine with no internet, and all the work goes into one shared Git repo.
    3. Each has a shell, a file editor, Send Message and Wait for Message. Anyone can message anyone.
    4. They're told to check the time with a terminal command and plan for the 24 hours.
    5. The repo is graded along the way. The charts show the best score reached by 2 hours, 6 hours and 24 hours.
    6. Each team size is run 3 times and averaged.

    The two tasks and how they're graded

    1. Knowledge base: read a company's documents and write indexed notes. Score = how many held-out questions a reader gets right using only the notes.
    2. Lean proof: prove a hard theorem in Lean from fixed statements. Score = the weighted share of 49 theorem statements the Lean checker accepts.

    Results: bigger teams got there much sooner. Final scores generally rose with team size, but by less each step. Opus 5.5 beat Opus 5 and Fable 5.1 at every team size on both tasks.2

    7 · How speed and cost are counted (team tests)

    A team can look fast just because the servers were quiet that day. So the cards don't use the wall clock. They rebuild each agent's time from its work.

    1. Count tokens. Every token that goes into an agent's context window, in or out, counts once per window. Add up all the agents.
    2. Price them. Tokens × the API list price, assuming every cache read hits. For example, Opus 5.5 is $4 per million input tokens and $20 per million output tokens.
    3. Time each agent from its work. Tokens ÷ fixed reference reading and writing speeds, plus the tool time actually measured.
    4. Carry the clock across hand-offs. A new helper starts at its creator's clock. An agent that gets a message jumps forward to the sender's clock if the sender's is later. That way waiting counts as time.
    5. Take the team's time. On ProgramBench it's the longest agent's clock. On DRACO it's the lead's final clock.

    8 · What changed in the harness between the two cards

    • Screen tests keep every screenshot now. The old setup threw away old screenshots. The new one keeps them all and summarizes the conversation once it passes 100k tokens. It also uses the 10 Sep 2026 task files. Fable 5.1 was re-scored this way (80.7% partial), which replaces its number in its own card.
    • The bug-hunting test was rewritten. It used to be called OSS-Fuzz. Bugs in the harness were fixed and settings changed, and every older model was run again. The new scores are higher, so they can't be compared with older cards.
    • The prompt-injection test got more time per turn in an updated Cowork harness, with the latest safeguards. The three older models were run again in it.
    • CAD pictures are now full size. The old setup fed 128 × 128 images instead of the intended 256 × 256. Older Claude models were re-scored, and Fable 5.1 went from 0.437 to 0.606 without tools.
    • New: the escape watcher, the time-pressure test, and the 100-agent teams.

    9 · Words used on this page

    Harness
    the program around the model that runs the loop: setup, tools, checks, memory, grading
    Agent
    one copy of the model running the loop on its own conversation
    Turn
    one trip around the loop: the model answers, and if it called a tool, the result comes back
    Tool call
    the model asking the harness to do something: run a command, edit a file, search the web, click
    Sandbox / container
    a sealed, throwaway computer where the tools run
    Classifier
    a small checking model that reads each turn and flags risky topics
    Backup model (fallback)
    an older model that answers a turn when a check trips
    Hard block
    a check that ends the conversation, with no backup
    Escape watcher
    a check that stops a run that tries to get out of its sandbox
    Adaptive thinking
    the model decides how long to think before each answer
    Effort
    how hard it tries: low, medium, high, xhigh, max. More effort means more tokens, so more cost.
    Token
    a piece of text, about ¾ of a word. It's how work and price are counted.
    Context window
    how much conversation the model can see at once, at most 1M tokens here
    Compaction
    squeezing older turns into a summary so the conversation fits
    Budget
    a cap on tokens, turns, actions or time for one try
    Trial / try
    one full run of a task. Scores average several.
    Pass@1 / Pass@3 / Pass³
    right on average per try / right at least once in 3 / right all 3 times
    Judge model
    another model that grades the answer against a rubric
    Derived latency
    time rebuilt from tokens and tool time, so busy servers don't skew it
